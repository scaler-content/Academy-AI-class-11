Section 1 · 9 minVibe coding, and the three habits

Vibe coding means you describe what you want, and an AI writes the code. You steer. It types.

It is fast. A working app in two minutes is normal now. And that is exactly the risk. The app looks fine, so you trust it, and the problems hide in the cases nobody tried.

A useful way to think about it: the AI is a very fast junior developer. It knows the syntax. It does not know your rules. Every rule you did not say, it guesses.

So the skill in this class is not typing prompts. It is three habits.

Habit What it protects you from
Spec first The AI guessing rules you never stated
Checkpoint before every change A fix that breaks something that worked
Review with a checklist, and test Code that looks right and is not

Use the visualizer below. Switch between a vague prompt and a spec, and see which decisions you made and which the AI guessed.

Ask LearnersThink of the last app you built or used that had a small bug in it. Which rule did nobody write down?

Most real bugs are not clever. They are a rule that lived in someone's head. A spec is where those rules go.

ImportantToday the bugs are not left to chance. The app you will review has six planted problems that always appear, so every learner sees the same thing, whatever their AI does. You will also use the AI as a reviewer and check what it reports.

Section 2 · 10 minSet up: editor, project folder, Git

NoteCursor is a code editor with an AI built in. It looks like VS Code, because it is built on it. Its menus and shortcuts change often, so if something below is named slightly differently on your screen, look in the menus.

Step 1 - Open Cursor and sign in with the free account.

Step 2 - Create a new folder called trip-splitter on your computer, and open that folder in Cursor with File, then Open Folder.

Step 3 - Open the terminal inside Cursor. It is under the Terminal menu. Check that Git is installed.

git --version

Step 4 - Tell Git who you are. This is needed once per computer. Use your own name and email.

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

Step 5 - Start Git in the folder.

git init

What a checkpoint is

Git keeps a history of your project. Each saved point in that history is a commit. Think of it as a save point in a game. You save before a risky move, and if the move goes wrong, you load the save.

Three commands are enough for today.

git add -A
git commit -m "describe what you just did"
git log --oneline

The first line stages every changed file. The second saves a checkpoint with a message. The third lists your checkpoints, newest first.

Two more let you look and undo.

git diff
git restore .

git diff shows exactly what changed since your last checkpoint. git restore . throws away changes you have not committed and returns the files to the last checkpoint.

Use the visualizer below. Commit a change that works, then one that breaks, and see what the history looks like.

ImportantThe habit is: checkpoint, then ask the AI, then test, then keep or undo. Never ask the AI to change a working file before you have a checkpoint.
Doubt by Learner"Cursor already shows me the changes and has an Undo button. Why do I need Git?"

The editor's undo is for the last few edits. Git is a named history you can return to a day later, compare against, and share. Also, AI tools can change several files in one go, and a checkpoint makes the whole change easy to review and reverse.

Section 3 · 14 minSpec first: ask for the Trip Splitter

A spec is a short written description of what you want, with the rules. We will give the AI the same request twice, once vague and once with a spec, and compare what each one decided for us.

Step 1 - Open the AI panel in Cursor and set it to Agent mode, so it can create files in your folder. The shortcut is usually Cmd+I on Mac or Ctrl+I on Windows, but check the menu if it differs.

Step 2 - First the vague one. Send this.

Make me a trip expense splitter web app.

Step 3 - Open the file it makes in a browser. Add two people, add an expense, and look at the result. Do not fix anything. Just note what it did.

Step 4 - Now go back to your last checkpoint, so the folder is clean. If you have not committed yet, delete the files the AI made. Then send the spec version.

Build a single-file web app, trip_splitter.html, with no libraries.
Users: friends on a trip. Every expense is split equally between everyone.
Features: add and remove people; add an expense (what it was for, amount, who paid); show the total, each person's balance, and who pays whom.
Rules: amounts are rupees with 2 decimals; reject empty names, duplicate names, and amounts that are not greater than 0; the shares must add up to the total to the paisa.
Safety: never insert user text into the page as HTML; keep no keys or secrets in the file.
Done when: the net of all balances shows 0.00 for any split.

Step 5 - Open that file in the browser, and try the same things. Then try three more: an empty amount, a negative amount, and splitting 100 between three people.

Ask LearnersWhich version made more of the rules, and which rules did you have to discover by trying?

Whatever your two apps did, the point is the same. The spec turned rules you would have had to discover into rules you can check. The last line, Done when, is the most useful, because it is a test you can run in ten seconds.

ImportantThe spec made the checks possible. It did not make the code perfect. A spec does not remove testing. It tells you what to test.

Switch to the class copy

Your AI's app is different from your neighbour's, and different again from mine. We cannot review the same code that way. So we all switch to one shared file.

Step 6 - Download trip_splitter.html from the class channel into your project folder. If you made your own trip_splitter.html, rename yours first so you keep it.

Step 7 - Open it in the browser. Add three people and an expense, to see that it works.

Step 8 - Make your first checkpoint.

git add -A
git commit -m "Class copy of Trip Splitter"
Note for InstructorSome learners will get a clean app from the vague prompt, and some will get one with problems. Both are fine. If a learner says "mine had no bugs", agree, and say that is exactly why the class gives everyone a copy with known ones. Do not tell the class the vague prompt always produces a worse app.
Doubt by Learner"If the AI can write a spec-quality app, why do I need to review it?"

Because the AI is checking against what it understood, and you are checking against what you meant. A good spec narrows the gap. It does not close it.

Section 4 · 16 minFind the bugs by testing, not by reading

Reading code you did not write is slow, and the bugs are not on the surface. A faster way: try to break it. Give it the inputs a real user would eventually type.

Here is a test sheet. Run each test on the class copy and write down what you see.

# Do this A correct app would
1 Add one person, Asha. Add an expense with the amount left empty. Refuse, and say why
2 Add one person, Asha. Add an expense of -500. Refuse, and say why
3 Click Add person with the name left empty. Then add Asha twice. Refuse both
4 Add Asha, Rohan, Meera. Asha pays 100. Read the line under Summary that says Net of all balances. Show 0.00
5 Add Asha and Rohan. Asha pays 500. Rohan pays 500. Read Top spender. Name both
6 Add Asha and Meera. Meera pays 100. Remove Meera. Not break
7 Add a person named <img src=x onerror="document.body.style.background='tomato'"> Show the text as it is
8 Open the file in your editor, and search it for sk_. Find nothing

Step 2 - Run test 4. Read the Net line. It says 0.01, and it should say 0.00. The app lost a paisa. Nobody typed a wrong number. The error is in how the money is divided.

Step 3 - Run tests 5 and 6.

Step 4 - Run tests 7 and 8. Test 7 turns the whole page red, which is harmless here. But the page ran text a user typed as if it were part of the app. Test 8 finds a key in the file.

Ask LearnersWhich of these could you have found by reading the code carefully, and which only by running it?

Some you could read. The 0.01 you almost certainly would not, because the code looks sensible. This is why the test sheet comes before the reading.

ImportantEach test maps to one question in your reviewer's checklist. Keep this table. It is the checklist you will use from now on.
Question to ask of AI-written code Tests
Are bad inputs rejected: empty, negative, zero, duplicate? 1, 2, 3
Does the money add up to the paisa? 4
What happens in a tie? 5
What happens when data is missing or removed? 6
Is any user text put into the page as HTML? 7
Is any secret in the file? 8
Doubt by Learner"Is the 0.01 a floating point bug? I heard computers cannot add decimals."

It is related, but it is not the whole story. The code also rounds each person's balance on its own, and three rounded thirds do not add back up to one whole. Even with perfect decimals, you would still have to decide who gets the extra paisa. That decision is one the AI cannot make for you.

Section 5 · 20 minFix one bug at a time, with checkpoints

We fix one bug, test, and checkpoint, then move on. Never ask the AI to fix everything at once: you cannot tell which change did what.

A good bug report to the AI has four parts: what you did, what you expected, what happened, and what to leave alone. Compare these two.

A weak one:

It does not work with money. Fix it.

A strong one:

In trip_splitter.html, when I add an expense with the amount left empty, the summary shows "Total spent: NaN".
Expected: the app refuses the expense and shows a short message.
Change only the add-expense and add-person code. Do not touch how balances are calculated.

Fix 1: what the app lets in

Step 1 - Send this to the AI. Make sure you are on a clean checkpoint first.

In trip_splitter.html, three things are accepted that should not be: an empty amount (the total becomes NaN), a negative amount, and an empty or duplicate person name.
Expected: the app refuses each one and shows a short message on the page. Duplicate names should be compared ignoring capital letters.
Also refuse an expense when there are no people.
Change only the add-person and add-expense code. Leave the balance calculation alone.

Step 2 - Run tests 1 to 3 again. Then run test 4 to check the rest still works.

Step 3 - Read the change with git diff, and then checkpoint.

git add -A
git commit -m "Reject bad names and amounts"

Fix 2: the money, and a fix that does not work

The 0.01 problem has an obvious fix. Many people, and many AIs, reach for it first. Try it by hand.

Step 4 - In trip_splitter.html, find this line.

const share = total / members.length;

Step 5 - Change it to round the share to two decimals.

const share = Math.round((total / members.length) * 100) / 100;

Step 6 - Run test 4 again and read the Net line.

It still says 0.01. Each person's share is now a tidy 33.33, but three of them make 99.99, and the app still thinks the total is 100.00.

Step 7 - Undo the failed fix. You have not committed it, so this returns the file to your last checkpoint.

git restore .
ImportantThis is why we checkpoint. You tried a plausible fix, it did not work, and one command undid it. Without the checkpoint you would be trying to remember what the file used to look like.

Step 8 - Now the real fix. Notice that it needs a decision only you can make: when 100 does not divide by 3, who pays the extra paisa? We decide that the first people in the list do. Send this.

In trip_splitter.html, splitting 100 rupees between 3 people makes "Net of all balances" show 0.01 instead of 0.00.
Expected: the shares always add up to the total exactly.
Store every amount as a whole number of paise, never as a decimal. Split the total in paise. When it does not divide evenly, the first people in the list pay one extra paisa each.
Change only the money code. Keep the page layout and messages as they are.

Step 9 - Run test 4 again. The Net line should say 0.00. Then try 10 split between three, and 0.07 split between three.

Step 10 - Checkpoint.

git add -A
git commit -m "Split money in whole paise"

Use the visualizer below. Set a total and a head count, and compare rounding each share against splitting in paise.

Fix 3: ties

Step 11 - Send this.

In trip_splitter.html, "Top spender" shows only one name when two people paid the same highest amount.
Expected: it names everyone who is tied, joined with "and". If nobody has paid anything, show nothing.
Change only the top spender code.

Step 12 - Run test 5. Checkpoint with a message of your own.

Fix 4: missing data

Step 13 - Look at test 6 again. Removing a person who paid breaks the page. There is more than one correct fix, and it is your call. The app could refuse the removal, or hand the person's expenses to someone else, or delete them. We choose the simplest: refuse. Send this.

In trip_splitter.html, removing a person who has paid for something makes the page stop working.
Expected: the app refuses to remove that person and shows a short message saying why. Removing a person with no expenses still works.
Change only the remove-person code.

Step 14 - Run test 6, then check that removing a person with no expenses still works. Checkpoint.

Ask LearnersIn Fix 2 and Fix 4, the AI could not have known the right answer. Why?

Because each had two or more correct answers, and the choice depended on what you want the app to do. The AI can write either. Only you can pick one. This is the part of the job that does not go away.

Note for InstructorIf time is short, demo Fixes 3 and 4 on screen and let learners do Fixes 1 and 2. Fix 2 is the one that matters most, because it contains the failed fix and the revert.
Doubt by Learner (Optional)"What if the AI's fix breaks something else?"

That is what the checkpoint and the other tests are for. After every fix, rerun the whole sheet, not only the test for that bug. If something that used to pass now fails, git restore . takes you back, and git diff shows what the AI touched.

Section 6 · 11 minThe quick security check

Two problems are left, and they are the ones that cause real damage.

Untrusted text

Step 1 - Look at test 7 again. The name you typed was not shown as a name. The browser read it as part of the page and built an image from it, and ran the code in its onerror. Here that code only turns the background red. In a real app, the same hole lets a stranger's text read other users' data.

The cause is one habit in the code: user text is put into the page as HTML. Find it.

$("members").innerHTML = members.map(...)

Step 2 - Send this to the AI.

In trip_splitter.html, names and expense descriptions are put into the page as HTML, so a name like <img src=x onerror="..."> runs as code.
Expected: any user text is shown exactly as typed and never treated as HTML. Do this everywhere user text is shown: people, the pay-by list, expenses, balances and the settle-up lines.
Change only how text is placed into the page.

Step 3 - Run test 7 again. The page should stay white, and the odd name should appear as plain text. Checkpoint.

Use the visualizer below. Type a name and compare how the buggy and fixed versions treat it.

ImportantThe rule is short. Text from a user is data, never markup. Whenever AI code puts user text into a page, a query or a command, ask how it keeps that text as data.

Secrets

Step 4 - Run test 8. The file has this near the top.

const API_KEY = "sk_demo_not_a_real_key_1234";

This one is a harmless fake. But AI tools often write real keys into files because you pasted one into the chat, or because it is the quickest way to make the code run. A file that reaches GitHub or a browser publishes the key to everyone.

Step 5 - Send this.

In trip_splitter.html, there is an API key written in the file. Remove it, and add a comment saying keys belong on a server, not in this file. Nothing else in the file should change.

Step 6 - Run test 8 again. Search the file for sk_ and find nothing. Checkpoint.

DisclaimerNever paste a real key into an AI chat or into a file you will share. If you ever do, treat the key as leaked, and create a new one in the provider's settings. Removing it from the file does not undo that.
Doubt by Learner"If the key is only in a front-end file and I never publish it, is it safe?"

Safer, not safe. Anything in a file that runs in a browser can be read by whoever opens that page. Real keys belong on a server, which Class 12 builds.

Section 7 · 8 minLet an AI review it, then check the reviewer

So far you found the bugs by testing. Now try the AI as a reviewer, because reviewing is something it is fast at. The key is to ask it to report only, and not to fix.

Step 1 - Download a fresh copy of trip_splitter.html from the class channel and save it as review_copy.html, so the AI sees the original problems and not your fixes.

Step 2 - Open the AI chat, attach review_copy.html, and send this. Change the file name in the prompt to match.

You are a code reviewer. Review the attached trip_splitter.html for bugs. Check these six things, and for each say Found or Not found, with the line it is on:
1. Inputs: are empty, negative, zero and duplicate values rejected?
2. Money: do the shares add up to the total to the paisa?
3. Ties: when two people are equal for top spender, what is shown?
4. Missing data: what happens when a person who paid is removed, or there are no people?
5. Untrusted text: is any user text put into the page as HTML?
6. Secrets: is any key or password in the file?
Do not fix anything. Only report.

Step 3 - Read the answer. Use the visualizer below. Tick what your AI reviewer reported, and what your own tests found, and see where the two overlap.

Ask LearnersDid the reviewer find all six? And did it say anything that was not true?

Whatever it did, you can now tell, because you have your own results from the tests. If it found all six, that is a useful reviewer. If it missed one, your tests caught it. If it claimed a bug that is not there, you found that out by running the code.

ImportantA reviewer's report is a list of claims. A test is evidence. Use the AI to widen what you look at, and use tests to decide what is true.
Note for InstructorThe reviewer's output was not checked here, so do not promise the class what it will find. Strong models often find most of the six. The lesson works whichever way it goes: if it finds all six, the point is that you still verified; if it misses some, the point is that tests found them.
Doubt by Learner (Optional)"Can I just let the AI both review and fix?"

You can, and it saves time. But keep the order: review, then you decide which findings are real, then fix one at a time with a checkpoint. A review that fixes as it goes gives you one big change you cannot read.

Section 8 · 9 minYour turn and wrap-up

Your turn. Add one feature to your fixed app, using every habit from today. The feature: some people do not share some expenses. For example, one friend did not eat at the dinner. Each expense gets a way to leave people out.

Step 1 - Checkpoint first. Make sure everything is committed.

Step 2 - Write a spec first. Four lines is enough. Here is a start. Finish it.

Feature: when adding an expense, I can untick people who do not share it.
Rules: an expense must be shared by at least one person; ...
Done when: ...

Step 3 - Add two of your own tests before you ask the AI. For example, an expense shared by only two of three people, and an expense with everyone unticked.

Step 4 - Send the spec to the AI. Run all the tests from this class again, not only the new ones.

Step 5 - Read the change with git diff. If anything broke that used to work, run git restore . and send a better bug report.

Step 6 - When it passes, checkpoint with a message that says what the feature does.

Ask LearnersWhich of your own rules did the AI not guess? Which test caught it?

What you now know. Vibe coding is fast and its risk is unstated rules. Habit one is a spec that puts rules in writing and ends with a line you can test. Habit two is a checkpoint before every AI change, so a bad change is one command to undo. Habit three is a review that combines a checklist, tests and, if you like, an AI reviewer, with the tests deciding what is true. The six questions to ask of AI-written code: inputs, money, ties, missing data, untrusted text, secrets.

What you built. A working Trip Splitter, six bugs found by testing and fixed one by one with checkpoints, and a feature added with the full loop.

Next class is the capstone. You will build a full app with a frontend and a backend and put it on the internet. You will use the same three habits at every stage: write a spec, checkpoint, test, and review. The security items you met today matter more there, because real keys live on the backend.
